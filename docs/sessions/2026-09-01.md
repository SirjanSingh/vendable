## Part one of the video

The decision that shaped everything: **no generative footage.** The submission's thesis is
that its claims are measured rather than asserted, and AI b-roll of a warehouse would
contradict that on screen. Every frame is a real artifact from this repo or a typographic
animation of a real result.

`docs/video/film.html` draws 0:00 to 3:00 and exposes `window.seek(t)`. Nothing is animated by
CSS transitions or by the clock; every visual state is derived from `t`. `render_film.py`
steps `t` in 1/30s increments and screenshots each one, so a dropped frame cannot silently
shift the picture against a voice track that does not exist yet.

Around it: `--probe` for stills, `--check` to prove determinism, `--pacing` to measure reading
load, and `build_film.py` to go frames → voice → the live take → one loudness pass, refusing to
call anything finished over 300s.

Deliberately **not** Remotion. It renders frame by frame and is deterministic the same way, so
it buys no correctness here, and it costs a Node and React install with a build step on drives
at 97% and 99% full, in a repo with no JavaScript tooling. Playwright was already a dependency.
Where Remotion would genuinely win is re-timing cues against a waveform; if that step turns
painful, reconsider there and only there.

## What the stills caught, which is the point of having them

**The architecture scene was wrong.** Fitted to the frame, the diagram's 12.5px body text
rendered at about 11px on a 1080p frame: under the legibility floor and precisely what
YouTube's encoder discards. It is now a camera that pushes in on each region. Smallest text on
screen is 22px; the parts carrying the argument are over 40px.

**My own kicker was set in caps**, breaking the sentence-case rule I had locked in
PRODUCTION.md an hour earlier. All caps costs 10-15% reading speed because identical letter
heights force letter-by-letter reading.

## The bug worth reading

`render_film.py` stopped parsing. A shell heredoc turned an escaped newline into a real one and
split a string literal in half.

What it looked like instead: a render in progress, writing correct 1920x1080 frames at the
expected rate, about two thousand of them. The background process had imported the module
*before* the edit and was executing the previous version out of memory. Running it proved
nothing. `ruff check scripts/render_film.py` also reported clean.

What caught it was `ruff check .` reporting **17 errors against a baseline of 14** — the count,
compared against a number I already expected, not any error text.

It is the fifth entry in `what-broke.md` and the cleanest instance of the pattern the other
four share. The output was not merely plausible, it was *correct*. The generalisation the
earlier entries were circling: **a check run against a process that loaded the code earlier is
not a check on the code.** Same boundary error as testing a storefront and reporting on a
transport.

The same shell layer then ate a backslash in a Windows path, turning `G:\v` into a vertical
tab, and split another `print()`. Escapes no longer go through heredocs.

## Pacing, measured rather than eyeballed

Two of the typography rules are arithmetic, so `--pacing` checks them without a person: peak
words on screen per cue, and the dwell of the final block against 3.5 words a second.

It found a real one on first run. **Scene 1 put 89 words of statute on screen in a 22-second
scene** — about 25 seconds of reading, with the type-on finishing 7.5 seconds before the cut.
Anyone watching would have seen a wall of legal text and been cut away from it. It is now 28
seconds, finishing at 11.0s, for 15 seconds of dwell. All six cues pass.

It also guards a failure that has not happened yet: frames are written by index and overwrite
in place, so a re-timed film **shorter** than the last render would leave its old tail on disk
for `build_film.py` to glob back in. The cut would play fine and be silently too long. Session
two re-times against real voice durations, which is exactly when that becomes possible.
