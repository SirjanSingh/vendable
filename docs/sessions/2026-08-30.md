## The two questions Phase 0 existed to answer

**Spike A — can a test payment complete headlessly? No.** Payment Links have no pay-by-API
endpoint; the UPI test VPAs belong to Checkout, not to any REST call; S2S JSON v2 is
support-gated per merchant. This invalidated an assumption that had been sitting under the
plan unexamined. Cost: one hour on day one, instead of a rewrite on day four. Resolution in
D-004 — a headless Playwright driver completes the hosted page, the payment stays real, and
the finding goes in the README because the gap between *an agent decided to buy* and *the
money moved* is exactly what agentic payment rails exist to close.

**Spike B — can a stock client connect by URL alone? Yes, proven.** `claude mcp add
--transport http` against a local server returned `✔ Connected` on an unmodified client, and
raw `server/discover`, `tools/list` and `tools/call` all returned 200 with annotations,
`outputSchema` and `structuredContent` intact.

Both were worth running. The research also caught, before any code depended on it, that MCP
spec 2026-07-28 removed the `initialize` handshake and `Mcp-Session-Id`, and that the SDK
renamed `FastMCP` to `MCPServer`. Verified by introspecting the installed package rather than
trusting the write-up — the correct instinct, and it paid.

## The GCP reversal

Mid-session: Cassandra's credits expire 31 Aug, billing detached, project gone. D-002 had
chosen it an hour earlier and was rewritten in place.

Honest assessment of the damage: **smaller than it first looked.** The risk the night-one
deploy existed to retire was never Cloud Run specifically — it was *can a stock client reach
my MCP server by URL and call a tool*, and that is answerable on localhost, which it now has
been. SQLite replaces Firestore with nothing lost, because the audit chain's integrity comes
from the hash chain and not from the store. `.env` replaces Secret Manager.

What genuinely defers: TLS, cold starts, multi-instance behaviour, and the
`TransportSecuritySettings` → `421` hostname trap. All four are pre-empted in code — allowed
hosts already read from an env var — but none is *proven*. This is now the top risk. If
billing does not arrive in time, the submission ships as a run-it-locally repo with a
one-command start, and the README says so plainly.

## Decisions taken

D-001 Python 3.13 everywhere, no local/container split · D-002 local-first, no GCP ·
D-003 caches and venv on D: · D-004 the payment leg needs a browser, and say so ·
D-005 the mandate is a tool argument, not a bearer header · D-006 prove the transport
locally on night one · D-007 `amount == cap` is allowed.

**D-005 is the one worth re-reading.** Claude Desktop's custom-connector dialog cannot send a
custom header — it takes a URL and optional OAuth credentials, nothing else. So the mandate
travels as a `create_purchase` argument. That forces a good property: because the buyer
supplies it, the server may trust *nothing* about it until it has verified signature, expiry,
audience and replay status itself. The transport constraint removed the temptation to
shortcut the gate.

## What the core actually does now

- **Money is integer paise, rates are integer basis points, and every rounding direction is
  chosen and justified.** `discount_bp` rounds up so no floor can be crossed by a rounding
  artefact; `price_at_margin` rounds up so the engine's own counter-offer satisfies the rule
  it was derived from. There is a test asserting exactly that, across a sweep of costs and
  floors.
- **The policy engine returns a counter-offer, not a bare refusal.** A gate that only says no
  makes the LLM guess again; one that says "no, and ₹93.34 is the best I can do" lets it close
  on the first retry.
- **The mandate gate fails closed everywhere.** No `amount_range` means refused, not
  unlimited. `alg=none` is never parsed. Replay is structural — a primary key on
  `(jti, cart_hash)` — because Razorpay has no idempotency header on Orders.
- **The audit chain does not claim immutability.** It claims detectability, and the tests
  prove it against payload edits, deletions, and a self-consistent forgery where the attacker
  recomputes the hash of the row they changed (caught one link later).

## Spike A resolved, and the answer reversed the plan

The morning's conclusion — "no headless test payment exists" — was **wrong**, and testing
beat reading. Against the live account: S2S is a hard 404 (not routed per-merchant), UPI is
disabled outright (`upi_type: {collect: 0, intent: 0}`), cards are defended by an RBI modal
plus hCaptcha. But **netbanking is enabled with 40 banks**, and choosing one redirects to
Razorpay's own `mocksharp` simulator — a page with a Success button and a Failure button, no
captcha, no OTP.

So the payment is fully headless after all, and the failure path is *deterministic*, which
matters more than it sounds: a declined payment that only happens sometimes cannot go in an
evidence table.

## Three bugs worth more than the features

**Prompt injection was the best deal on the menu.** Live, the agent gave an honest buyer 2%,
a pushy one 7%, and an attacker **10%** — because the hostile fallback handed out maximum
authority. Every price cleared the floor; every test passed. The bug was economic, not
structural, and no stub test could have found it because they all asked "did the floor hold"
rather than "does attacking pay better than asking".

The fix improved the design rather than patching it: discount authority split into
**entitlement** (the published volume break — published means owed, so quotes carry it
automatically) and **discretionary** (the ageing allowance, the only thing a negotiation can
win). Then the mirror image appeared — negotiating politely returned ₹12.00 against
`request_quote`'s ₹11.25 — and the entitlement became a *floor on the outcome*. Both bugs were
one mistake in two costumes: three code paths each deriving "the price" independently.

**A false accept found by counting, not attacking.** The red team scored 37/37. The confusion
matrix then found that the gate compared the *mandate's* currency to the *cart's* currency —
both buyer-supplied, so an attacker can make them agree. A EUR mandate against a EUR cart was
authorised at a merchant that settles only in INR. Fixed by checking against server-side
merchant configuration. The instruments ask different questions and building both was right:
the red team probes hypotheses I already had, the matrix enumerates a grid.

**A 400 that arrived as a 500.** The webhook rejection path wrote to a locked SQLite file.
WAL plus a busy timeout made it rarer; one shared connection per file removed the contention.
Given a choice between tuning a retry and removing the race, remove the race.

## Deliberate limitations, published

The red team returned three findings that are trade-offs rather than defects: refusal messages
name the exact floor price (actionable errors are specific, and specific is informative); 11
unauthenticated probes binary-search that floor; and a politely-worded injection evades every
scanner pattern while the policy engine holds the line anyway. All three are in `SECURITY.md`
with the mitigations I did not implement and what they would cost.

# Session 2 — India-shaped policy, and two bugs found by counting

Picking up here from another machine? Everything below is current as of commit `26f73fe`.
Remote is `github.com/SirjanSingh/vendable` (**private**). 216 tests, all green.

## What shipped this session

**Payment terms as a price lever** (`D-008`). `payment_terms_days` flows through
`request_quote` and `negotiate`. A rung is earned by falling *inside* a window, not by
clearing a threshold — the inverse of the volume ladder — so paying sooner is never worth
less. The discount is **entitled, not discretionary**: it joins the volume break because it
is published and therefore owed. Terms are inside the `cart_hash`, so taking the 2/10 price
and then paying at 60 days is a different cart and gets refused by the existing tamper check.

**The MSMED s.15 guard** (`D-009`). `MerchantPolicy.statutory_max_credit_days()` — the
statute as a pure function, no model call. It is the only control here that protects the
*buyer*: an autonomous agent would otherwise book a longer credit period as a win, while
triggering compound interest at 3x the RBI bank rate (s.16) and deferring its principal's own
deduction (s.43B(h)). The exclusions matter as much as the rule — medium enterprises are out,
Udyam **traders** are out of 43B(h).

**Two merchants**, each a directory (`catalog.json` beside `policy.json`). The hardcoded
`MerchantPolicy(...)` literal is gone from `mcp/server.py`.
- `acme-fasteners` — registered small **trader**, unconstrained, Net 60 fine
- `shakti-forgings` — registered small **manufacturer**, capped at Net 45

The demo: both are asked for Net 60 on the same goods. Shakti is cheaper at every terms level
and still has to refuse. Verified live:

```
1000 x hex bolt M10x50, buyer wants 60 days
acme     Net 10 Rs 18.70   Net 30 Rs 19.14   Net 60 Rs 19.14
shakti   Net 10 Rs 17.92   Net 30 Rs 18.42   Net 60 REFUSED (msmed_limit_exceeded)
```

## Three bugs, none found by attacking

1. **Catalog reads ignored `merchant_id`** (`D-010`). The column and its index existed from
   the first schema; every read ignored both. Two storefronts on one SQLite file served each
   other's SKUs at their own margin floors. Caught by a smoke test reporting 41 SKUs for a
   17-SKU merchant.
2. **The gate matrix raced its own clock.** An evidence file claiming to reproduce on any
   machine gave 62/62, 61/62, 62/62 on identical code. A 1-second-TTL mandate case against a
   `now` sampled once at the top. Widened to 30s.
3. **The engine approved a sale at -11.79% margin.** `PIPE-GI-40`, ~Rs 230 lost per unit,
   `violations=[]`, explanation reading "Approved". `validate_product` had flagged it blocking
   the whole time — nothing connected that report to the sales path. Now a hard
   `LIST_BELOW_FLOOR` gate. Written up in `what-broke.md`.

Also corrected: the README claimed **three** LLM calls. There are two. The policy compiler was
planned and cut, and the README was claiming it in the section the rubric rewards.

## N1: the engine is insurance against the tail, not the median

## Two experiment bugs, both caught before the paid run

Both would have published confident nonsense; both are in `what-broke.md`.

1. **The N2 line had zero discretionary authority.** `BOLT-M8-40` is 45 days old, unlocks no
   ageing rung, so the engine floored every outcome at the entitlement and all seven
   categories returned an identical 1000.0bp. Seven matching rows look like a clean result,
   not a bug. Moved to `BOLT-M12-75` (200 days, 500bp of discretionary room).
2. **`run_n1` ignored `--runs`**, so a breach rate would have rested on n=4.

The pattern across this and the two earlier misses (a syntax error passing 179 tests, an
evidence file claiming determinism while flickering): **check what the number would look like
if the thing being measured were absent.**
